# Odyssey 웹 프론트

게시 전에 사진·글 속 개인정보를 확인하고 보호 편집하는 6단계 화면이다. 백엔드 게시물 API(`/api/posts`)를 쓴다.

## 실행

Node.js 20 이상.

```sh
npm ci
VITE_API_TARGET=http://10.1.1.27 npm run dev
npm run dev
```

- 첫 번째 줄(`npm ci`) 다음에 서버 API를 쓰려면 `VITE_API_TARGET=...` 줄을 실행한다 (VPN 필요).
- 로컬 백엔드(localhost:8000)를 쓰려면 그냥 `npm run dev`를 실행한다.
- 둘 다 http://localhost:5173 에서 확인한다. `/api` 요청은 개발 서버가 백엔드로 넘겨 주므로 CORS 설정이 필요 없다.
- 배포 때는 `odyssey-web` 이미지가 이 프론트를 빌드해서 Nginx로 서빙한다.

## 백엔드 없이 편집 화면 보기

`frontend`에서 `npm run dev` → http://localhost:5173 → **예시로 먼저 둘러보기**를 누르면 바로 편집 화면으로 들어간다. 기존 카페 사진에 텍스트·객체·간접 위치 단서 샘플 영역이 표시된다. 네모 모서리의 크기 조절·× 삭제와 일반 편집 효과, 결과 미리보기·다운로드를 서버 없이 사용할 수 있다.

화면 데모에서는 API를 호출하지 않으며 실제 탐지·재검증 결과로 표시하지 않는다. Gemini 이미지재생성은 비활성화한다. 실제 업로드 흐름으로 돌아가려면 홈의 **바로 보호 편집하기**를 선택한다.

## 화면 흐름과 API

| 단계 | 하는 일 | API |
| --- | --- | --- |
| 01 홈 | 새 게시물 보호로 시작. 이전 게시물 점검은 준비 중 | - |
| 02 업로드 | 사진 최대 4장(JPG·PNG·WebP, 한 장 10MB) + 함께 올릴 글 | `POST /api/posts` |
| 03 분석 결과 | AI ① 탐지 + ② 위험 분석 결과. **추천 보호안 보기** → 04, **건너뛰기** → 06 | `GET /events` (awaiting_user), `GET /report` |
| 04 보호 편집 | 기존 2열 화면, 유형별 도구, 모서리 크기 조절·× 삭제 | 일반 편집은 Canvas/OpenCV, 이미지재생성만 `POST /api/images/regenerate` |
| 글 확인 | 글에 단서가 있으면 원래 글과 AI가 고친 글을 보여 주고 적용하기 / 건너뛰기 | - |
| 05 재검증 | 브라우저에서 완성한 사진·본문을 새 게시물로 분석. 편집 내역과 잔여 단서 표시 | `POST /api/posts`, `GET /events` (awaiting_user), `GET /report` |
| 06 공유 | 브라우저에서 만든 최종 파일 공유(Web Share)·다운로드·본문 복사 | 추가 요청 없음 |

- **사진 순서:** 사진 순서가 `position`이다. 서버는 사진마다 작업을 만들고, 글은 0번 사진과 함께 분석한다.
- **미리보기와 저장:** 같은 Canvas 렌더러를 사용한다. 크기·강도·생성 패치를 포함한 결과를 PNG로 다시 그려 EXIF를 제거한다. 기존 `/transform` API는 다른 클라이언트를 위해 유지하며 이 화면에서는 호출하지 않는다.
- **유형별 도구:** 텍스트는 가림/블러/부분마스킹/텍스트제거, 객체는 가림/블러/모자이크, 간접위치는 가림만 표시한다. 이미지재생성은 일반 편집 도구와 분리해 사진 바로 아래 패널에서 실행한다. 영역별이 아니라 사진 한 장의 영역(텍스트·객체·간접위치)을 한 번에 새로 그린다. 지운 영역과 "그대로 두기" 영역은 빼고, 생성한 영역은 도구 목록에 이미지재생성이 추가되어 다른 방법으로 바꿨다가 되돌릴 수 있다. `finding.category`가 있으면 우선 사용하고, 없으면 기존 `source/type`으로 분류한다. 모르는 유형은 객체로 처리한다.
- **효과:** 가림은 불투명 덮기, 블러는 픽셀 평균화, 모자이크는 작은 격자를 확대한다. 블러·모자이크는 선택만 가능하며 반경/격자 크기는 고정값 16px이다. 사용자 상세 설정은 없다. 부분마스킹은 탐지 네모 안에서 사용자가 드래그한 사각형만 가린다. 임의의 중앙 비율은 사용하지 않으며 범위 지정 전에는 적용을 막는다. 글자·단어를 선택하는 OCR 기능은 아니다.
- **텍스트제거:** 선택할 때만 OpenCV.js를 로드하여 Telea 인페인팅을 실행한다. 선택 영역 전체를 주변 배경으로 채우며 글자별 마스크는 사용하지 않는다. 큰 영역은 주변 포함 최대 512px로 처리한다. 복잡한 무늬는 부자연스러울 수 있고 전체 사진을 선택하면 주변 픽셀이 없어 오류를 표시한다. OpenCV 별도 청크는 약 15.5MB(압축 약 3.9MB)이며 초기 화면에는 로드하지 않는다.
- **영역:** 네 모서리를 직접 드래그하여 중심과 비율을 유지하며 크기를 조절한다. 사진 경계에서 확대를 멈추고 짧은 변이 12px 아래로 축소되지 않는다(원래 더 작은 영역은 원래 크기가 최소). 이동·추가는 없으며 네모의 × 버튼으로 영역과 해당 보호 처리를 삭제한다. 기존 되돌리기로 삭제·크기·효과를 복구한다. 슬라이더나 임의의 20% 경고는 없다.
- **키보드 조작:** 모서리에 초점을 맞추고 방향키로 크기를 조절한다. 부분마스킹은 영역에서 Enter → 방향키로 시작점 이동 → Enter → 끝점 이동 → Enter로 지정한다. Shift는 10px, Escape는 취소다. × 버튼도 키보드로 사용할 수 있다.
- **이미지재생성:** 게시물 ID나 분석 상태 없이 전처리된 사진(`file`)과 그 사진의 영역 좌표 목록(`boxes`)을 독립 API로 보내고, AI 한 번 호출로 영역 순서대로 배경(`patches`)을 받는다. 현재 화면은 AI가 처음 추천한 보호 처리(추천 처리 방법·AI 영역 크기)를 브라우저에서 적용한 사진을 넘긴다. 사용자가 바꾼 편집(보호 방법, 영역 크기, 삭제, 부분마스킹, 이전 생성 결과)은 넣지 않으며(`flow.ts`의 `generationBase`), 화면에도 그렇게 안내한다. 영역 좌표는 생성 결과를 채울 현재 영역이다. 재생성할 영역도 가린 상태로 보내며 원본 픽셀로 되돌리지 않는다. AI 워커가 만든 전처리 사진도 같은 API로 전달할 수 있다. 서버는 전처리 완료 여부를 판별하지 않으므로 호출자가 처리본을 전달해야 한다. 서버에서 Gemini를 호출하고 반환된 선택 영역만 합성한다. 생성 실패는 일반 편집 적용을 막지 않는다. 다른 영역의 보호는 유지한다. 사진별 최초 1회 + 재생성 2회 제한은 App의 React 상태에서만 관리하고 실패한 요청도 차감한다. 편집 화면 재진입·추천 초기화·추가 보호 시 유지되며 새 입력이나 새로고침 시 초기화된다. DB/Redis에는 횟수를 저장하지 않는다. 프론트 UI 제한이므로 API 직접 호출에는 적용되지 않는다. GET은 서버의 생성 키 설정 여부만 확인한다.
- **설정:** API 서버 `.env`에 `GEMINI_API_KEY`, `GEMINI_IMAGE_MODEL`을 설정한다. DB 스키마 변경이나 추가 마이그레이션은 필요 없다. 키가 없으면 생성 버튼을 비활성화한다. 이미지는 이 엔드포인트의 메모리에서만 처리하고 S3에 추가 저장하지 않는다. 생성은 2,400만 화소 이하를 지원한다.
- **재검증:** 브라우저의 최종 파일을 기존 분석 API로 보내 잔여 단서를 확인한다. PNG 결과도 장당 10MB 제한을 적용하고, 빈 사진·본문은 재분석하지 않는다. 추가 보호는 결과 사진을 다시 분석해 편집하되 처음 사진의 생성 예산을 유지한다.
- **원본:** 브라우저 메모리에만 보유하므로 새로고침하면 사진을 다시 선택해야 한다.
- **03 건너뛰기:** 서버를 거치지 않고 사진을 PNG로 다시 그려 파일 정보(EXIF)만 지운 채 06으로 간다.

## 검사

```sh
npm test
npm run build
```

테스트는 다음을 확인한다.
- 게시물 요청: 사진 순서와 글, 변환 때 원본 재전송
- 진행 대기: `awaiting_user`에서 멈추는지
- 파일 검사: 수·크기·형식, 잘못된 영역 좌표
- 리포트 → 단서 변환과 영역 라벨(A, B, C)
- 변환 선택(`choices`)
- 글 가림: 워커와 같은 규칙
- 그대로 둔 단서와 재검증 단서 짝짓기
- 결과 파일의 바이트·MIME·파일명, 사진 1·3·4장과 처리된 본문 공유, 파일 공유 미지원·취소

공유 버튼은 브라우저에서 완성한 파일과 본문을 `navigator.share`로 전달한다. HTTPS와 지원 브라우저가 필요하며, 미지원 환경에서는 다운로드·본문 복사를 안내한다.
파일 공유 지원 여부는 `navigator.canShare({ files })`로 검사한다. 사진이 빠지고 글만 전달되는
일을 막기 위해 파일 공유 지원을 확인할 수 없는 환경에서도 다운로드·본문 복사를 안내한다.

기기 확인: HTTPS의 iPhone Safari에서 합성 사진 1·3·4장과 가짜 본문을 보호 처리한 뒤,
공유 → X를 선택해 사진 수·순서·보호 결과·본문을 확인한다. 사진만, 본문만, 공유 취소 후
재시도도 확인한다. 공유 Promise 완료는 X 게시 완료가 아니며, 확인 과정에서 실제 게시할
필요는 없다. 자동 테스트는 공유 API를 대체하므로 실제 기기의 공유 시트는 별도로 확인해야 한다.

## 이번 편집 확장의 검증

단위 테스트는 분류별 허용 도구, 네 모서리 확대/축소의 중심·비율 고정과 경계 제한, 블러 픽셀과 생성 요청을 검사한다. 합성 사진과 가짜 API를 사용한 headless Chrome 검사로 기존 2열 화면, 이동 불가, 직접 크기 조절, × 삭제·복구, 사용자가 그린 부분마스킹, 상세 슬라이더 없음, 생성 3회 제한, 모바일 가로 넘침, 미리보기와 재검증 업로드 파일의 바이트 일치, 브라우저 인페인팅을 확인한다.

실제 Gemini 생성 품질·iPhone 터치/공유는 이번 작업에서 실행하지 않았다. 복원·생성 품질과 잔여 개인정보는 결과를 직접 확인해야 한다.

브라우저 회귀 검사는 Node 22 이상에서 `npm run dev`와 별도 임시 Chrome 프로필을 실행한 뒤 `npm run test:browser`로 재현할 수 있다. 모든 API를 합성 응답으로 대체하므로 실제 AI 호출은 없다. macOS Chrome 실행 예시:

```sh
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --no-first-run --remote-debugging-port=9229 --user-data-dir=/tmp/odyssey-editor-check about:blank
npm run test:browser
```

검사 후 해당 Chrome과 Vite 프로세스는 종료한다. 화면 캡처는 `/tmp/odyssey-editor-desktop.png`, `/tmp/odyssey-editor-mobile.png`에 저장된다.
