# 개인정보 보호 편집 UI와 API 기록

기록일: 2026-10-31. 로컬 코드 및 `x-api-test` 테스트 기록 기준. 신규 경로는 설계 제안이며 아직 구현된 API가 아니다.

과거 기록과 현재 코드가 다르면 현재 구현을 기준으로 판단한다. 아래 원본 삭제·재전송 흐름은 로컬 구현에 반영했다. 실제 서버·AWS에는 아직 적용하지 않았다.

## 2026-11-01 편집 확장 반영

현재 프론트는 일반 편집과 최종 PNG 저장을 브라우저에서 처리한다. 완성한 사진·본문을 기존 `POST /api/posts` 분석으로 재검증하며 `/transform`은 화면에서 호출하지 않는다. 아래 기존 변환 계약 설명은 기존 API/다른 클라이언트에 해당한다.

- 원격의 2열 화면을 유지한다. 텍스트: 가림/블러/부분마스킹/텍스트제거, 객체: 가림/블러/모자이크, 간접위치: 가림. 이미지재생성은 간접위치 영역을 선택했을 때 별도 패널에서 실행한다. 이동·추가 없이 네모 모서리에서 중심·비율을 유지하며 크기를 조절하고 ×로 삭제한다. 블러·모자이크는 선택만 가능하며 고정 강도를 사용한다. 부분마스킹은 사용자가 네모 안에서 직접 지정하며 중앙 비율을 정하지 않는다. 텍스트제거는 필요할 때 불러오는 OpenCV.js 인페인팅이다.
- `POST /api/images/regenerate`: Gemini 영역 생성. 불필요한 설정 조회 GET은 제거하고 키 미설정은 POST의 503 응답으로 안내한다. 게시물 ID·DB·큐와 독립적이며, 호출자가 전처리한 사진과 영역 좌표를 전달한다. 현재 화면은 AI 탐지에 따른 브라우저 보호 처리본(대상 영역도 가림)을 사용하며 AI 워커 처리본도 같은 계약으로 연결할 수 있다. API 서버 키 설정만 필요하다. 사진별 생성 3회(최초 1 + 재생성 2) 제한과 실패 요청 차감은 프론트 React 상태에서 관리한다. DB 스키마 변경이나 Redis 카운터는 없다. 편집 화면 재진입 때는 유지하고 새 입력·새로고침 때 초기화한다. API 직접 호출을 제한하는 기능은 아니다. 실제 모델 호출은 검증하지 않았다.
- 상세 동작·기술적 한계·검증은 `frontend/README.md` 기준이다. 이미지/본문을 브라우저 영구 저장소에 보관하지 않는 원칙은 유지한다.

## 화면 흐름

홈 → 사진/본문 업로드 → 위험 단서 분석 → 영역별 보호 편집 → 재검증 → 공유.
편집 상세: 영역 선택 → 처리 방법 선택 → 미리보기 → 수정 요청/다시 생성 → 적용·재검증 → 잔여 위험 추가 보호.
참고 디자인: 사용자가 제공한 밝은 하늘색 배경, 남색 제목, 파란 기본 버튼의 6단계 한국어 화면.

## 현재 API

| 메서드 | 경로 | 기능 |
| --- | --- | --- |
| POST | `/api/jobs` | 사진 1장, 텍스트 또는 사진+텍스트 업로드·분석 시작 |
| GET | `/api/jobs/{id}` | 상태 조회 |
| GET | `/api/jobs/{id}/events` | SSE: progress, awaiting_user, done, timeout |
| GET | `/api/jobs/{id}/report` | AWAITING_USER/DONE 작업의 탐지·위험 리포트 |
| POST | `/api/jobs/{id}/transform` | AWAITING_USER 작업에 원본 파일과 idx/action 선택을 재전송하여 변환·재검증 |
| GET | `/api/jobs/{id}/result` | DONE 작업의 결과 URL 및 본문 |
| GET | `/health`, `/api/health` | 동일한 서버 상태 확인 기능 |

현재 입력 제한은 파일 10MB, 텍스트 5,000자. 이미지 디자인의 20MB와 다르므로 실제 API 기준을 사용한다.
README 일부에 transform/AWAITING_USER 설명이 누락되어 있으므로 코드가 기준이다.

## 제안하는 신규 API

| 경로 | 목적 |
| --- | --- |
| `GET /api/jobs/{id}/versions` | 이전 처리 결과·미리보기 및 적용 버전 조회. 삭제된 원본은 제공하지 않음 |
| `POST /api/jobs/{id}/apply` | 선택한 버전을 적용하고 재검증 시작 |
| `POST /api/jobs/{id}/analyze` | 지정한 버전의 심층 분석; 결과는 report 재사용 |

재검증은 apply에 통합하여 별도 verify API를 생략한다. 독립 재검증이 필요하면 추가한다.
이전 작업 목록을 제공할 때만 `GET /api/jobs?cursor=…`가 필요하다. 원본 미리보기는 프론트 메모리의 파일을 사용하며 서버에서 복구하지 않는다.

## 기존 API 확장

- jobs: 여러 사진 `files[]`와 공통 본문, 사진별 ID·순서. X 시연은 최대 4장.
- transform: 고정 finding ID, image ID, 선택 영역/마스크, 교체 문구·추가 요청, 기준 version ID. 미리보기·재생성·추가 편집을 같은 API로 처리.
- report: 항목별 위험 등급·설명, 해결/잔여/신규 위험, 기존 보호 유지 여부. 탐지 신뢰도 score와 위험 등급은 별개.
- result: 적용된 버전의 `images[]` URL·MIME·파일명과 처리된 본문.
- 상태/SSE: 편집 실행과 버전 식별, 미리보기 준비·적용 상태 구분.
- DB: 현재 작업별 결과 한 건 upsert를 버전별 보관으로 확장.
- 워커: 현재 최초 findings 스냅샷을 Phase 2로 전달해 선택 인덱스 변경을 방지했다. 버전 간 추적까지 확장할 때 고정 ID 도입.
- 다중 사진·버전은 API뿐 아니라 Redis 계약, DB, AI 워커도 함께 변경해야 한다.

## 현재 Redis / JSONB / S3 구현

1. 프론트 → 백엔드: 업로드·변환은 multipart/form-data. 변환에는 file과 JSON 배열 문자열 choices를 보낸다.
2. 백엔드가 원본을 S3에 저장하고 Redis jobs 스트림 payload에 JSON 문자열을 넣는다.
3. 워커는 object_key와 AWS 자격 증명으로 S3 원본을 읽는다. 워커 입력은 presigned URL이 아니다.
4. 워커가 결과를 S3에 쓰고 results 스트림에 결과 키·본문·리포트 JSON을 보낸다.
5. 백엔드가 DB에 저장한다. findings/details는 PostgreSQL JSONB이다.
6. result API가 기본 300초 유효한 presigned GET URL을 SDK로 생성해 반환한다.

## 원본 삭제·편집 재전송 흐름 (로컬 구현, 운영 적용 전)

- S3 사용은 유지한다. 원본은 작업 전달을 위한 임시 객체, 처리 결과는 조회·공유용 객체로 구분한다.
- 프론트는 선택한 원본 File을 화면 세션의 메모리에만 보유한다. 서버는 업로드를 S3에 임시 저장하고 object_key를 Redis JSON 메시지로 워커에 전달한다.
- 워커는 원본을 읽어 탐지한다. 탐지 완료 직후 서버 측 S3 원본 객체를 삭제하고 원본 바이트 참조를 해제한다. 에이전트2에는 탐지 결과를 전달한다. 탐지 결과를 Redis 체크포인트에 기록한 뒤 원본을 삭제한다. 실패·타임아웃도 정리하며 삭제 실패 시 완료 결과를 보내거나 큐를 ack하지 않고 재시도한다.
- 프론트에는 민감 원문을 제외한 사용자 선택용 리포트를 제공한다. 현재는 최초 findings 스냅샷과 idx를 보존하여 사용자가 본 항목을 편집한다. entity_id 전환은 다중 사진·버전 계약 확장 시 진행한다.
- 사용자가 보호 방법을 선택하면 프론트 메모리의 원본 파일과 선택한 idx/action을 다시 전송한다. 서버가 SHA-256으로 최초 파일과 일치하는지 확인하며, transform API는 multipart의 file과 choices를 받는다.
- 편집 입력도 S3에 임시 저장하고 object_key로 전달한다. 워커는 편집 결과를 originals/의 임시 편집본과 Redis 체크포인트로 남긴 뒤 재전송 원본과 메모리를 정리하고 결과를 재검증한다. 성공·실패 결과를 발행하기 전에 임시 편집본도 삭제한다. 편집 실패·타임아웃에도 원본을 정리한다. 원본을 읽기 위한 별도 재탐지로 사용자 선택을 재매핑하지 않는다.
- 처리 결과는 S3에 저장하고 결과 object_key를 백엔드로 반환한다. 백엔드가 presigned URL을 발급하여 프론트 조회·다운로드·X 공유에 사용한다. 처리 결과의 보관 기간은 별도로 확정해야 한다.
- 새로고침·탭 종료로 프론트 원본이 사라지면 사진을 다시 선택해야 한다. 서버에 원본 복사본을 남겨 복구하지 않는다.
- URL 만료는 객체 삭제가 아니다. 실제 삭제 동작과 버킷의 버전·보관 설정도 함께 확인해야 한다.
- 사용자가 기존 수명 주기는 1일이라고 확인했다. README의 설정 안내는 originals/ 접두사에 생성 후 1일 만료이다. 실제 AWS 규칙의 적용 범위는 직접 조회하지 않았다. 이 규칙은 누락 객체 정리용으로 유지하고, 탐지 직후 삭제는 워커의 명시적 삭제로 처리한다. S3 Lifecycle의 Days는 최소 1일이며 UTC 자정 기준 계산과 비동기 처리로 정확한 24시간 삭제를 보장하지 않는다. 근거: https://docs.aws.amazon.com/AmazonS3/latest/API/API_LifecycleExpiration.html 및 https://docs.aws.amazon.com/AmazonS3/latest/userguide/troubleshoot-lifecycle.html
- AI 워커 기본 버킷과 .env.example을 백엔드와 같은 odyssey-hackarton-images로 맞췄다. 실제 실행 환경변수는 별도 확인해야 한다.
- 큐 계약 v2는 execution_id를 필수로 가진다. 요청마다 별도 임시 키를 사용하며 결과 소비자는 현재 실행과 일치하는 QUEUED 작업만 갱신한다. 기존 v1 워커와 혼용하지 않는다.
- DB 마이그레이션 0002는 input_sha256/execution_id를 추가한다. 이전 분석 작업은 파일 해시가 없으므로 다시 업로드해야 한다.
- 워커는 실행별 잠금과 완료 결과 캐시를 사용한다. 체크포인트 기록 후 원본을 삭제하며 재시작하면 그 지점에서 재개한다. 체크포인트 기록 자체가 실패한 경우에도 원본 삭제를 우선하므로 재업로드가 필요할 수 있다. 체크포인트·완료 캐시 보관은 progress_ttl_seconds(기본 24시간)이며 만료 후에는 새 업로드가 필요할 수 있다.
- 탐지 항목이 없어도 이미지 결과를 재인코딩해 메타데이터를 제거한다. 사용자가 skip한 픽셀은 그대로 남을 수 있으므로 결과 파일도 원본과 별도로 보관·삭제 정책이 필요하다.
- 삭제는 해당 originals/ 키의 모든 버전과 삭제 마커를 제거한다. API와 워커에 ListBucketVersions 및 originals/*의 DeleteObject/DeleteObjectVersion 권한이 필요하다. AWS 정책은 아직 변경하지 않았다.
- Compose의 API /tmp와 Nginx 업로드 버퍼 /tmp는 tmpfs로 설정했다. Compose 외 로컬 실행에서는 업로드 파서가 임시 디스크 파일을 만들 수 있다. 메모리 참조 해제는 보안 소거 보증이 아니다.
- DB/Redis 장애로 등록 자체가 실패한 업로드는 API에서 삭제를 시도한다. 이 삭제까지 실패하면 기존 1일 수명 주기가 최후 정리 수단이며, 즉시 삭제를 보장하지 않는다.
- 현재 Gemini 테스트 경로는 외부 서비스로 사진을 전송한다. S3 삭제가 외부 서비스 데이터 삭제를 뜻하지 않는다. 합성 테스트 자료만 사용하는 기존 범위를 유지한다.

## X 공유 시연

`../x-api-test/XShareWeb/README.md` 기록: 2026-10-31 iPhone iOS 27.2 Safari에서 텍스트, PNG 1/3/4장+본문, JPEG 3장+본문, PNG 1장 단독 전달 성공. 5장은 AbortError. Android/PC는 미확인.

- 신규 share API, X OAuth, 직접 게시 API는 필요 없다.
- 현재 UI: 브라우저에서 완성한 File[] → navigator.share({ files, text }). 사진 순서와 처리된 본문을 함께 전달한다. 기존 서버 변환 클라이언트는 게시물 result의 `/api/jobs/{id}/image`를 fetch해 File[]을 준비한다.
- 사진 파일은 버튼 클릭 전에 준비한다. 공유 시 사용자 활성화가 필요하다.
- 같은 서버의 이미지 API를 사용하므로 S3 CORS 설정은 필요 없다. 공유 시트에는 HTTPS가 필요하며, 테스트의 로컬 가짜 이미지 전달과 실제 S3 결과 전달은 별도 통합 검증 대상이다.
- 결과 레코드·사진 키 누락은 result API가 404로 응답한다. 이미지 API는 S3 파일 누락을 404, 저장소 연결·권한 오류를 503으로 응답한다. 파일 공유 지원은 `canShare({ files })`로 확인하고, 미지원 시 다운로드·본문 복사를 안내한다.
- 공유 반환은 실제 X 게시 완료를 보장하지 않는다. 성공 기준은 X 글쓰기 화면의 사진·본문 확인이다.
- Instagram/YouTube 직접 연동은 현재 구현 범위가 아니다.

## React 테스트 UI 범위

기존 frontend에서 구현. 화면 데모는 로컬 샘플과 브라우저 편집으로 흐름을 확인한다. 실제 API 모드는 기존 엔드포인트만 호출하며 사진 한 장+본문과 분석/변환/결과를 연결한다.
미구현 심층 분석·생성 편집을 실제 AI 호출처럼 위장하지 않는다. 사진/본문은 새로고침 후 복구를 위해 브라우저에 영구 저장하지 않는다.
현재 AI 코드는 Gemini 기반 탐지와 블러·마스킹·메타데이터 제거를 구현한다. 자연스러운 이미지 제거는 아직 불투명 가림으로 처리한다. DONE을 개인정보 안전 보증으로 표현하지 않는다.

## 검증 범위

초기 API 조사와 X 결과 확인은 정적 코드 및 기록 검토였다. 실제 서버·S3 CORS·기기 공유의 재시험은 수행하지 않았다.

React UI 1차 구현: 기존 frontend를 6단계 반응형 UI로 교체. 기본 화면 데모와 실제 API 모드를 구분했다. 기존 API의 image_text, AWAITING_USER SSE, transform 연결을 추가했다. 신규 백엔드 API는 구현하지 않았다.

검증: TypeScript/프로덕션 빌드와 핵심 테스트 5개 통과. 실행 환경에서 포트 바인딩이 EPERM으로 거부되고 Chrome 실행도 실패하여 브라우저 시각/기기 공유 검증은 미수행. 실행과 수동 확인 절차는 frontend/README.md 참조.

원본 수명 변경 검증: 백엔드 47개(추가 subtest 37개), AI 31개, 프론트 5개 테스트 및 프론트 프로덕션 빌드 통과. S3 버전 삭제는 moto, 워커 재시작·삭제 실패·전송 재시도는 가짜 Redis/S3로 검증했다. 마이그레이션 0002의 PostgreSQL SQL 생성과 변경 Python 파일의 Ruff 검사를 완료했다. 실제 AWS·DB 적용·Gemini 호출·기기 공유·배포는 수행하지 않았다.

투명 PNG/WebP는 흰색 배경에 알파 합성한 뒤 RGB로 처리하여, 투명 픽셀에 숨은 RGB가 탐지·편집 결과에서 드러나지 않게 한다. 해당 회귀 테스트를 추가했다.

PR 준비 검증: 이전 분석 결과의 늦은 Redis 상태 갱신이 새 편집 SSE를 종료하지 않도록 보완하고 회귀 테스트를 추가했다. 예시 사진 버튼은 화면 데모로 전환한다. 실제 외부 모델 호출과 서버 배포는 수행하지 않았다.
